## 使用者、工作與情境

主要使用者：好日子科技的員工。他們想請假，以前用訊息送出，送完不知道有沒有登記成功，也沒有地方查（Brief §問題與證據）。這次要讓員工送出後馬上確認已登記，而且隨時查得到自己的申請（G-01）；不合法的申請要被擋下，不能留下資料（G-02）。系統沒有登入，員工從下拉選單選自己。

主流程：開啟 LeaveBot → 從下拉選單選自己 → 填假別、開始日期、結束日期、時段與理由（選填）→ 按「送出」→ 畫面顯示「已送出、待審核」和系統算出的天數，「我的假單」立刻多出這一筆。

失敗流程：輸入不合法時，後端拒絕並顯示原因，資料庫不新增資料；表單保留已填內容，員工改完可以再送。網路錯誤也一樣處理。資料存在 SQLite，重新整理頁面或之後重新進入，選同一位員工時仍看得到這些申請，而且只看得到自己的。

## 故事與驗收條件

以下例子都假設系統時鐘固定在 **2026-10-28（週三）**。員工 A、員工 B 代表預先提供的名單中任兩位員工，名單內容留給 SRS/SDS 決定（Brief §假設）。

### US-01 送出假單並立即知道登記成功（G-01）

身為員工，我想送出請假申請並馬上看到結果，以便確認已經登記成功，不必再去問。

- AC-01.1：Given 已選員工 A When 送出特休（annual）、2026-11-02（一）至 2026-11-04（三）、整天、理由「家庭旅遊」 Then 畫面顯示「已送出、待審核」，天數為 3；員工 A 的「我的假單」立刻出現這一筆，狀態是「待審核」。
- AC-01.2：Given 已選員工 A When 送出以下申請 Then 系統依工作日算出天數並存檔，使用者無法自行指定天數。
  - 事假、2026-11-06（五）至 2026-11-09（一）、整天 → 2 天（週六、週日不算）。
  - 病假、2026-11-06（五）單日、上午 → 0.5 天。
- AC-01.3：Given 今天是 2026-10-28 When 員工 A 補請病假（sick）、2026-10-19（一）至 2026-10-20（二）、整天 Then 申請被接受，天數為 2，狀態是「待審核」（D-02）。
- AC-01.4：Given 已選員工 A When 理由留空，或只填空白字元，其他欄位合法 Then 申請被接受，這筆假單的理由視為未填（D-01）。
- AC-01.5：Given 已填好合法申請 When 按下「送出」，回應還沒回來時又連點 Then 第一次按下後按鈕立即停用，連點不會再送出，最後只新增 1 筆；收到回應後按鈕才恢復（D-03）。

### US-02 不合法的申請被擋下且不留下資料（G-02）

身為員工，我希望填錯時系統直接告訴我哪裡錯了，以便修正後再送，也不會留下錯誤的假單。

- AC-02.1：Given 員工 A 目前有 N 筆假單 When 送出下表任一筆不合法的申請 Then 後端拒絕，畫面顯示拒絕原因；員工 A 仍是 N 筆，資料庫沒有新增任何資料。

  | 例子 | 違反的規則 |
  |---|---|
  | 沒選員工，或選的員工不在名單中 | 必填、員工存在 |
  | 沒填假別、開始日期、結束日期或時段其中一項 | 必填 |
  | 假別不是 annual／personal／sick，或時段不是整天／上午／下午 | 假別與時段合法 |
  | 開始 2026-11-04、結束 2026-11-02 | 結束日期不早於開始日期 |
  | 2026-11-07（六）至 2026-11-08（日） | 範圍內至少有一個工作日 |
  | 2026-11-02 至 2026-11-03、上午 | 半天限單日 |

- AC-02.2：Given 其他欄位合法 When 理由去掉前後空白後剛好 200 字（例如 200 個中文字，前後再各加 2 個空白） Then 申請被接受；When 去掉前後空白後是 201 字 Then 後端拒絕並顯示原因，資料庫不新增資料。中文、英文、標點都算 1 字（D-01）。
- AC-02.3：Given 申請被拒絕，或送出時發生網路錯誤 When 畫面回報失敗 Then 「送出」按鈕恢復可按，已填內容保留，畫面顯示失敗原因；員工改正後再送一次合法申請，就會依 AC-01.1 成功（D-03）。

### US-03 查看自己的假單（G-01）

身為員工，我想看到自己送過的所有申請和狀態，以便隨時確認，不必另外詢問。

- AC-03.1：Given 員工 A 有 2 筆假單，員工 B 有 1 筆 When 下拉選單選員工 A，再切換成員工 B Then 選員工 A 時只列出 A 的 2 筆，選員工 B 時只列出 B 的 1 筆。每筆至少顯示日期範圍、假別、時段、天數與狀態「待審核」。
- AC-03.2：Given 員工 A 剛依 AC-01.1 送出一筆假單 When 重新整理頁面，再選員工 A Then 這一筆仍在列表中，內容和送出時一致。

## 產品規則與體驗

正常情況下，員工不必知道任何規則：選自己、填表、送出，就會看到成功訊息和系統算好的天數，列表跟著更新。只有輸入不合法時才會看到原因；表單內容不會消失，改完就能再送。新假單一律是「待審核」，這次沒有人會改變它的狀態。

| 情境／規則 | 使用者看見的結果與資料變化 | 來源／AC |
|---|---|---|
| 理由長度 | 選填；去掉前後空白後最多 200 字，超過時拒絕並且不存檔 | D-01；AC-01.4、AC-02.2 |
| 過去日期 | 可以補請，系統不和今天比較 | D-02；AC-01.3 |
| 連點送出 | 送出期間按鈕停用，只新增 1 筆 | D-03；AC-01.5 |
| 成功後又送出相同內容 | 系統不去重，會新增第 2 筆，兩筆都出現在列表 | D-03、NG-04 |
| 錯誤後修正 | 保留已填內容、按鈕恢復，改完可以再送 | D-03；AC-02.3 |
| 天數與狀態 | 由系統計算或固定為「待審核」，使用者無法指定 | `03-LEAVEBOT.md`；AC-01.1、AC-01.2 |
| 理由內容 | 以純文字保存與顯示；輸入 `<b>x</b>` 時畫面照原樣顯示這幾個字元，不會變成粗體 | `03-LEAVEBOT.md`、D-01 |

「成功後又送出相同內容」不另寫成 AC：這是本組接受的風險（Brief §風險），不是要保證的功能。

## 範圍、依賴與待決

- 非目標：沿用 Brief 的 NG-01～NG-05，包括登入、主管核准／駁回、國定假日、特休額度、同組人數、自動去重、附件、LLM 解析與部署。
- 依賴：員工名單要預先提供。AC 用員工 A／B 代表名單中的人，實際名單在 SRS/SDS 決定。
- 產品決策：D-01～D-03 沿用 Brief 的決策紀錄，本文件沒有新增決策。
- 待決（不阻塞主線，決策人：本小組，期限：寫 SRS 前）：
  - 「我的假單」的排序方式，以及員工沒有假單時顯示什麼。
  - 拒絕原因的實際文案，以及是否逐欄標示錯誤。目前 AC 只要求「顯示原因」。
  - 理由存檔時是否去掉前後空白，以及「未填」存成空字串還是空值。D-01 只規定先去空白再算字數。

> 審查重點：每個 G 有使用者結果；成功、拒絕與資料持久性可判斷；核心規則有來源；待決問題不被寫成已確認需求。
