## 偏差紀錄

### 票 001｜`invalid_body`、`invalid_type`：SDS 要求實作，測試計畫列為「不測」

- 現象：
  - 測試計畫把這兩個錯誤碼列為「不測（已知缺口）」，沒有對應的 TC。
  - SDS API-03 的錯誤碼表卻要求實作。
  - 不實作的後果：陣列本文、格式錯誤的 JSON、日期傳數字，都會讓 API 拋出未處理例外並回 500。
- 處理：
  - 依 SDS 實作，並用紅綠燈補 3 個測試（陣列本文、格式錯誤的 JSON、非字串值）。
  - 這 3 個測試的 marker 是 `req("未編號", ...)`，沒有自行編 TC 號碼。
  - 測試計畫本身沒有改。
- 待決：小組決定是否在 06 補成正式 TC（例如 TC-13），還是維持「已知缺口」，只把這些測試當成防護。
- 發現時間：2026-10-28，票 001 檢查點 6 後審視 `validation.py` 時發現。

### 票 001｜TC-12 改用 8001 埠

- 現象：8000 埠被一個既有的 `uvicorn --reload` 占用（PID 9208）。這個程序用系統 Python，不是 `.venv`，看起來是骨架驗收時手動啟動的。
- 處理：
  - 沒有關閉這個程序，改在 8001 埠啟動。
  - 啟動時設定 `LEAVEBOT_DB` 指向暫存檔。
- 提醒：這個程序沒有設定 `LEAVEBOT_DB`。重新載入新程式後，只要有請求進來，就可能建立 `backend/data/leavebot.db`。執行結束時這個目錄不存在；小組可以自行決定是否關閉該程序。

### 票 001｜部分 TC 一寫就是綠燈

- 原因：前面的 TC 已經驅動出所需的程式。
  - TC-03、TC-04：天數邏輯已由 TC-02 完成。
  - TC-07b：去空白已由 TC-07a 完成。
  - TC-09 的 E002、E003 查詢：篩選條件已由排序測試完成。
  - TC-10、TC-11：檔案型 SQLite 和參數化 SQL 本來就具備這些行為。
- 處理：用暫時的變異確認測試確實會抓到錯誤，確認後已還原。
  - 天數改成日曆天數：TC-03a、b 轉紅。
  - 啟動時刪表：TC-10 轉紅。
  - 存檔前做 HTML 跳脫：TC-11 轉紅。
- TC-04 在「日曆天數」變異下仍然綠燈，因為 10-19～10-20 中間沒有週末。它守的是「不拒絕過去日期」，不是天數計算。

## 規格誤解

### SRS X-01｜「今天」的固定值，課程材料與 PRD 例子不一致

- 歧義來源：
  - `course/01-上課/04-STACK.md` 寫：「若規則使用今天……課堂固定 `2026-10-12`」。
  - `docs/02-prd.md` 的例子假設今天是 2026-10-28。
- 影響：本專案依 D-02 不和「今天」比較，所以沒有規則或 API 契約受到影響。受影響的只有 AC-01.3 和 TC-04 的前提：如果今天是 10-12，例子中的 2026-10-19 就成了未來日期，這個案例就測不到「補請」。
- 處理：已列為 SRS X-01，等講師裁定。在裁定前，測試先注入 2026-10-28；如果改成 10-12，TC-04 改用 2026-10-05～10-06，預期仍是 2 天（`docs/06-test-plan.md`）。
- 發現時間：2026-10-28，寫 SRS 時對照 STACK 發現。

## 踩過的坑

- **`sqlite3` 跨執行緒**：同步 dependency 在執行緒池開連線，`async` 路由卻在事件迴圈的執行緒使用它，於是拋出 `ProgrammingError`。改用 `check_same_thread=False`。這樣做安全，因為每條連線只屬於單一請求。
- **`--import-mode=importlib` 下不能 `import conftest`**：共用的常數要透過 fixture 提供，或直接寫在測試檔裡。
- **資料表約束會提前擋下錯誤**：TC-05b、c 的紅燈是外鍵錯誤，TC-06c 的紅燈是 `CHECK (days > 0)` 被轉成 500。這證明第二道防線有效，但第一道驗證仍然要補上，錯誤才會是 422 和正確的錯誤碼。
